# POD 毛毯长任务 Agent（pod-blanket）

[Last Updated: 2026-10-27]

## 目标

依据《POD 毛毯设计拆解与长任务 Agent 方案 v1》（原件在 `source/`，不入库），在 DeerFlow 上搭一个长任务 agent：
把爆款参考图拆成 14 维可控设计字段，并判断这张图上哪些字段能变 → 程序从可变字段里随机挑着自动策划裂变方向（**小变化**每个随机改两个小变化字段、构图不动；**大变化**改主题 / 构图 / 画法中的一个字段，或随机三个小变化字段一起改；2026-10-27 起线上每轮小变化 30（八成至少一处换主体）+ 大变化 24，小变化出完后再以换了主体的小变化图为底图出 16 个二次大变化）→ **挑选方向**（系列规则一并认可；2026-10-22 起程序自动全部确认，`batch.auto_confirm_directions`，关掉回到人工挑选）→ 只往选中的方向出图（2026-10-27 起只跑 gpt-image-2.5-sunburst：小变化只做图生图 1 张；大变化文生图 + 图生图 2 张），一直出到全部出完 → 独立质检 → 人工选款（相近的候选不判重复，一并交给人挑）→ 选中的款交给 mooya 的图案管线出套图（白底图 + 场景图）；后台由网关定时器每 10 分钟巡检推进。

给用户的使用说明：一页版 `skills/public/pod-blanket/references/usage.md`；详解版（每一步的规则、审核项效果、触发方式、卡片、配置、排查、命令）`skills/public/pod-blanket/references/guide.md`。

## 架构

```
飞书 / Web ──对话──▶ pod-blanket 人设（custom agent）──bash──▶ podctl CLI ──▶ podflow 引擎
飞书渠道定时器（每 60 秒）──▶ podctl tick --auto ──到点──▶ tick ──拉起──▶ 后台 worker（主租约 + batch.workers 条工位，共用生图 / LLM 名额）
长任务 --detach ──▶ bg_tasks 登记 + 后台 podctl 进程 ──结束──▶ 完成 / 失败卡片（--notify）
podflow 引擎 ──▶ 业务库：mooya Postgres 的 pod_blanket 库（seed / analysis / family / variant / job / asset / 调用账本 / 审核 / 事件 / 后台任务 / 上传记录）
            ──▶ 素材：mooya OSS 主桶 pod-blanket/ 前缀为准（按 seed / family / variant / asset 版本分目录，不覆盖），本机做缓存
                  写入 → 本机 + storage_objects 待上传 → 后台 podctl storage sync（单上传进程，可限速）
            ──▶ mooya LiteLLM :4001：gpt-6.1-sol-high（P01–P07、P11 结构化阶段）+ gpt-image-2.5 flare / sunburst × 文生图 / 图生图（flare 兼做 S01P 图案提取，失败换 sunburst）
选款完成 / 出套图 ──▶ scene_sets 排队 ──▶ 后台 podctl scenes sync（单租约）──▶ mooya /api/service/v1（服务令牌）──▶ 图案管线 skip_dna 毛毯 job
                  ◀── 查进度、逐张拉原图 ──┘ 存 assets/scenes/ + 套图压缩包 exports/scenes/ → OSS，选款表写四列，发「套图出完」卡片
套图收尾 / 巡检 ──▶ shelf.sweep（seed_shelf：有新动静的调出；shelf.auto 时做完的归档）──▶ 表格同步按 folder_state 用 Base v3 块接口挪候选表进 / 出「已归档」文件夹

```

- **模型提出、程序执行**：每个 Pxx 阶段是一次独立调用（G00 + Pxx），输出过 JSON Schema（`schemas/`）与程序校验，不合格带错误说明重答；领取、预算、状态、重试、计划去重全由程序做。
- **P00 程序化**：`podctl tick` 按 P00 规则判断（暂停 / 试运行窗口 / 预算 / 积压 / worker 存活 / 空队列 / 系列耗尽），只拉起一个后台 worker。
- **长耗时转后台**：沙箱 bash 单条命令 600 秒超时，结构化阶段单次调用 1–6 分钟（M1 用 gpt-5.6-sol-high 实测 S01→S04 合计约 13.5 分钟），所以 `seed analyze` / `family revise` / `plan` / `worker` 都可 `--detach`。后台进程统一由 `podflow/bg.py` 拉起并登记在 `bg_tasks`（子进程靠 `PODFLOW_BG_TASK` 认领登记行，结束记 done / failed；进程死了登记还停在 running 的，查询时改记 failed）；`--notify` 时结束发完成 / 失败卡片。
- **飞书工作台**：fork 飞书渠道（`backend/app/channels/fork/pod_cards.py` + `pod_bridge.py`）以子进程调 `podctl ui dashboard / tasks / reviews / daily / timeline / gallery / originals / directions / history` 取视图 JSON 渲染卡片，按钮直接调 `podctl review decide` / `plan [--hint=…] --detach --notify` / `directions pick|confirm --pick … --start|reject --replan` / `worker --detach --notify` / `trial` / `tick` / `pause` / `resume`，不经过大模型。业务措辞、「下一步」规则、按钮与参数都在引擎的 `podflow/ui.py`，渠道只负责渲染和参数校验。

- **裂变方向挑选**（`podflow/directions.py`）：S05 只出候选方向（批次 `proposed`、变体带 `title / brief / keep / aspects`，不建任务），开 `plan_selection` 待审；挑选卡是根节点表单里的勾选清单，勾选只在飞书本地，提交时一次带上（`confirm --pick`；对话里的勾选存在批次 `plan_json.picked`，卡片上默认勾着）。确认时：选中的建任务与槽位、其余记人工没选（下次 P05 的排除项）、待认可的系列一并认可，`--start` 拉起只推进这些任务的后台出图（`worker --job …`）。之后每轮 worker 结束（先接选款修改）、巡检（不看连续运行窗口）、`resume` 都会接上，直到这些方向全部出完才发卡片。
- **定时巡检**：飞书渠道启动后起一个进程内定时器，每 60 秒调 `podctl tick --auto`；到没到巡检间隔、日报时刻由引擎按 `podflow.yaml` 的 `schedule` 判断（记在 meta `last_auto_tick_at` / `last_daily_report_day`），没到点不写事件。

## 风险

- 预算关闭期间，定时巡检的花费只受批次大小（CFG09）、worker 时限、试运行窗口与审核积压上限约束；开 24 小时试运行前应重新评估。每个任务出的张数：最初 3 张，2026-10-13 起 6 张，2026-10-15 起 9 张，2026-10-25 起大变化 4 张、小变化 2 张（见下）。
- 去掉 S08 后没有任何自动检查拦「照抄参考图」（质检只看候选图本身）；图生图把参考图（2026-10-20 起是提取的图案）喂给模型，授权未知也做——靠选款时并排看参考图、由用户把关。
- 质检存疑 / 未经质检的图和人工修改版都不再停下等人或自动复检，只靠选款时人看；选款积压会因此略涨（原来停在质检待审的图现在直接进选款）。
- 参考图是带沙发、房间的商品照时，图生图可能把场景也保留：2026-10-20 起先做图案提取再图生图。提取本身也会走样（S01 实测把画面放大铺满、留白变少，题材、配色、水彩质感都保住了），只能靠「图案已提取」卡片上人眼核对，不满意就带要求重新提取。
- 套图依赖 mooya：mooya 宕机、令牌轮换、预设下线时套图停住（`doctor` 报错、全局退避，恢复后自动接上）；mooya 改了场景数量或步骤，这边照单全收（按 mooya 给的 `expected` / `images`）。套图的模型费用发生在 mooya 那边（租户 `platform_internal`），不进 pod-blanket 的调用账本和预算。
- 交付包每批次约 30–40MB × 款数（首批 8 个包 73–520MB，共约 2GB），每有新款出完就整包重打、重新上传；款数多的批次重打一次要几十秒，会占 OSS 空间（旧包删掉，只留一份）。链接和「下载套图」一样，拿到链接的人都能下载。
- gpt-6.1-sol-high 慢且没有跨供应商冗余（anyaigc 单一渠道）。2026-10-25 起出图只剩 flare / sunburst，二者是同一 anyaigc 渠道的两个别名：这个渠道出问题时所有出图一起停（之前的 nano-banana 2.1 也只有 anyaigc 一家）。
- 2026-10-15 到 10-25 每个任务出 9 张（Edit 那张和图生图同一路由，只是多一次采样），并发 9。2026-10-25 起大变化 4 张、小变化 2 张，并发 4；每轮方向翻倍（24 + 16），一轮约 112 张图（比之前的 144 张少），P06 每个方向调一次；2026-10-26 前任务一个接一个出，一轮 40 个方向约 3 小时（之前 20 个方向实测 1.6–2 小时），之后 8 条工位同时出，瓶颈变成 P06 的 LLM 名额（3 个，P06 40–140 秒一次）和上游生图能扛多少。
- 视觉识别会出错（M1 把小象认成考拉），系列规则必须人工把关。2026-10-22 起方向自动确认，系列规则随之自动认可、没人先看：认错了的方向会直接出图，只能看完成卡片 / 任务明细后修订系列、停掉没开始的方向。
- 方向自动确认后每张新图约 144 张出图（预算关着）：只受 `batch.review_backlog_limit`（线上 1500）约束，开关打开时选款积压已是 1428，新图出到积压满 1500 就停新出图，选款处理掉一些后自动接上。
- 方向记录按字段进 P05（每个字段最多 12 条、每条目标值 ≤ 40 字）：比整份记录短，但每轮方向多了，几轮之后两轴组合那组的上下文会变长。
- 每轮 30 个左右方向：策划约 5–10 分钟（12 组 / 4 并发，按实测调 `plan.concurrency`）；全选时一轮出图 200 多张，费用与选款量都明显上升（预算仍关闭）。
- 拆解的可变判断会出错（像 M1 认错小象）：挑选卡顶部列出不适用的维度、不能变和锁定的字段，判错了在 POD 对话里修订系列。
- 小变化靠 P06 最小改动写法 + P07 对照原图守构图：模型没守住时质检判修复，修两次还不行由人在选款里点「不要」或写意见修改。
- 勾选清单要飞书 V7.9+：更老的客户端看不到勾选框，只能在 POD 对话里说「B00x 选 1、3」。
- 选款表的原图下载链接是 OSS 签名链接：有效期内拿到链接就能下载（不需要登录），只能靠表格权限和不外传来控制；要立刻作废只能轮换 OSS AK。表格由应用创建，协作者是最近在卡片上选款的人；换人要配 `table.share_with` 后 `table init --reset`。
