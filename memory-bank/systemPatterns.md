## 1. 技术架构与运行拓扑

- 飞书 WS 长连接 → gateway 进程内 `ChannelService` → `ForkChannelManager` → Gateway 的 LangGraph 兼容 API（nginx `/api/langgraph/*` → `/api/*`）→ `lead_agent` → `task` 工具 → 角色子代理 → `bash` → `cursor-agent`。
- 渠道地址：Docker 内由 compose 注入 `DEER_FLOW_CHANNELS_LANGGRAPH_URL` / `DEER_FLOW_CHANNELS_GATEWAY_URL`，`config.yaml` 不写 `langgraph_url` / `gateway_url`。
- 持久化：DeerFlow 主库（ORM 业务表 + LangGraph 检查点 + Store）2026-10-29 起是 mooya Postgres 的 `deerflow` 库（`database.backend: postgres`；ORM 走 asyncpg，检查点 / Store / 入站去重走 psycopg；启动时 bootstrap 在 advisory lock 下 `alembic upgrade head`）。pod-blanket 业务库是同实例的 `pod_blanket`。SQLite 只剩 DeerMem 检索索引。11-02 起 SQLite 旧库已删、不能再回滚到 `sqlite`，恢复靠 `pg_restore` Postgres 备份（`backup_pod_blanket.sh`，`PG_DATABASE=deerflow`）。
- 上游把 IM 请求的 run 身份解析为 `_channel_storage_user_id(msg)`：已绑定是 Web 账号 id，未绑定是 `safe(open_id)`。它同时决定文件桶和记忆桶。本部署 `channel_connections.require_bound_identity: true`，未绑定请求在 manager 入口被拒。

## 3. IM 渠道模式

- **store 扩展字段**（按 `channel:chat_id`，不分 topic）：`workdir` / `workdir_history`（MRU 8）/ `agent`（人设展示缓存）/ `model` / `sessions{thread_id: {title, agent, model, workdir, created_at, updated_at}}`（上限 50）；`channel:user:<open_id>` → `chat_id`。所有读写持 `_lock`。
- **人设**：真正生效的是线程钉住的 agent（上游 `_thread_agent_names` + 线程 metadata `channel_agent_name`）。fork：`/agent <名>` 改写为 `/agent use <名>`；`_create_thread` 未指定 agent 时沿用 store 里的人设（校验失败则回落默认）；未钉住的线程回落该会话存的人设。
- **模型**：`store.model` 仅在仍在 `config.models` 中时注入 `run_context["model_name"]`（网关按白名单校验，不在白名单会直接 400）。
- **工作目录**：消息前缀 `[当前工作目录：X。未明确指定其他路径时…]`；`normalize_workdir` 只接受 `sandbox.mounts` 各根的直接子目录，拒绝穿越。
- **会话**：登记在 ChannelStore；「当前会话」指针走 `_lookup_thread_id` / `_store_thread_id`（已绑定在连接库，未绑定在 store）。已绑定且无 topic 时 fork 再把指针镜像进 store（chat 级），会话快照（人设 / 模型 / 工作目录）才会同步到真正的当前会话。删除当前会话后切到剩余最近的一条，没有则新开。绑定后第一次查找会尝试沿用 store 里的旧指针（owner 读得到才写入连接库，每个会话只试一次）。卡片切换发 `/sessions _gcswitch`，卡片删除先本地移除再发 `_gcdelete`；两者都只接受 `fork_source=card_action`。
- **流式进度**：`StreamProgressObserver` 追加 `custom` 流模式；只有 `values` / `custom` 重算进度，消息块只刷新活动时间。todos / 子任务写入 outbound metadata（`fork_progress_todos` / `fork_progress_steps`）；子任务首次失败发 `fork_notification`（仅飞书）。`ForkChannelManager._handle_streaming_chat` 退出时 `close()`，避免最终回复发送失败后快照一直停在 running。`LiveRunRegistry` 供 `/status`（含子任务累计 token）。
- **POD 工作台**（`fork/pod_cards.py` 的 `PodCardsMixin`，由 `ForkFeishuChannel` 混入）：
  - **入口：** 裸 `/pod`、菜单 `POD` / `POD_CHAT`、`pod_*` 按钮。只在单聊（`store.get_user_chat(open_id) == chat_id`）且已绑定时可用。
  - **数据：** 视图来自 `pod_bridge.PodBridge.run("ui", …)`，即子进程 `sys.executable podctl.py`，30 秒超时，`{"error"}` 或非 0 退出码转 `PodctlError`。
  - **回调：** 按钮先回 toast，再用 `_schedule` 在主循环里调 podctl、上传缩略图（`(path, mtime)` → image_key 的 LRU 256），最后 `_patch_card(open_message_id, card)`。
  - **动作：** `pod_plan`（`family_id` 须 `^F\d+$`；方向数由引擎按可变字段定，按钮里的 `limit` 一律忽略、不传）→ `plan --family F [--hint=<要求>] --detach --notify`（要求取 `form_value["hint_<F>"]`，压空白，> 100 字回 warning toast；`back == "tasks"` 时提交后渲染任务列表，其他值回工作台）；`pod_tasks`（`offset` 非负）→ `ui tasks --offset n --limit 4`；`pod_history`（`family` 可省、须 `^F\d+$`，`offset` 非负）→ `ui history`（任务明细卡）；`pod_plan_view`（`batch` 须 `^B\d+$`）→ `ui directions`；`pod_plan_pick`（旧卡片；`variant` 须 `^V\d+$`、`on` 只认 0 / 1）→ `directions pick [--off]`；`pod_plan_confirm` → `directions confirm --by feishu:<open_id> --start`，带 `form_value` 时追加 `--pick`（值为 true / "true" 的 `^pick_(V\d+)$`，按编号排序），一个没勾回 warning toast 不调引擎；`pod_plan_reject` → `directions reject --replan --notify` 后回工作台；`pod_worker` → `worker --detach --source feishu --notify`；`pod_trial_start|stop` → `trial … --by feishu:<open_id>`；`pod_timeline` / `pod_gallery`（`batch` 须 `^B\d+$`）；`pod_send_originals`（`asset_id` 须 `^IMG\d+$`）→ `ui originals` 后逐个调上游 `send_file(OutboundMessage, ResolvedAttachment(is_image=False))` 发文件消息，> 30MB 跳过。
  - **下一步按钮：** 引擎给 `{"action", "label", "style", **参数}`，`_step_button` 去掉 label / style 后原样作回调值。
  - **待审项布局：** `_review_elements` 对两张及以上图片的项排成「标题 → `_image_row`（按引擎给的顺序并排，选款是原图在左）→ 说明」；单张或没有图片时用 `_media_block`（图左文右）。
  - **定时器：** `_pod_timer_start()`（`ForkFeishuChannel.start()` 里上游 `_running` 为真才调）每 60 秒 `podctl tick --auto`，异常 2 倍退避到 1800 秒、成功复位；模块级 `_timer_owner` 保证进程内只起一个；`stop()` 先 `_pod_timer_stop()`、`_pod_bitable_stop()` 再调上游。没装 skill（`podctl_path()` 不存在）不起。
  - **候选表事件（2026-10-23）：** `_event_handler_builder` 多注册 `register_p2_drive_file_bitable_record_changed_v1(self._on_bitable_record_changed)`。lark 线程里：`file_token` / `table_id` / 记录 id 须 `^[A-Za-z0-9_-]{4,64}$`、操作人须 `^ou_…`，`_ticked_records(action_list)` 只留 `record_edited` 且 `after_value[].field_value` 为 true / "true" 的记录，没装 skill 直接丢；再 `_schedule(_pod_bitable_collect)` 到主循环，按 (file_token, table_id) 合并记录、`POD_BITABLE_DEBOUNCE_SECONDS`（2 秒）后 `_pod_bitable_flush` → `podctl table control --file --table --records a,b --by feishu:<open_id>`，出错只记日志（`[Pod] bitable control`）。判断是不是表顶的按钮行 / 交付包行、是不是真勾着全在引擎。
  - **POD 对话：** 进入 = 找会话快照 `agent == pod-blanket` 的最近一个，`switch_session` 后发 `_gcswitch`；没有就发 `/agent use pod-blanket`。进入前把当前会话写进 store 的 `pod_return_thread`（不进快照）。
  - **卡片内表单：** `_review_form` 在卡片根节点放 form（`input note_RVxx`，`required / multiline_text / max_length / default_value / fallback` + `form_submit` 按钮，值带 `field`）；`feishu.py` 把 `event.action.form_value`（只收 dict）放进 `CardActionContext.form_value`；`_form_text(ctx, field, pattern=_FIELD_RE)` 默认只认 `^note_RV\d+$` 字段，`pod_decide` 的 `needs_changes` 没意见时回 warning toast，有意见追加 `--note`。挑选卡的勾选清单：表单上面（表单外）是引擎 `pick_actions` 给的「全选 / 全不选」（`pod_plan_pick_all`，`on` 0 / 1 → `directions pick B all [--off]` 后原地刷新）；根节点 form（`pick_Bxxx`）里每个方向一个 `checker`（`name pick_Vxxxx`、`lark_md` 文本、`overall_checkable`、`checked_style` 不划线不变淡、**不配 behaviors**，只在本地切换，要 V7.9+），`_direction_rows` 排行：item 带 `section` 时换段插一行段标题、段内不加 `hr`（几十个方向，40 个时卡片 JSON < 28KB），没有 `section` 的旧批次相邻之间 `hr`，最后 `_form_submit`；任务明细卡和任务列表卡的 form（`plan_Fxx`，`_plan_form`）是 `input hint_Fxx`（`required: false`）+ 提交；任务列表一张卡上可以有多个（每个已完成 / 待策划的任务一个，表单名按系列区分）。按钮都由引擎给的 `form.submit` 经 `_form_submit` 加 `name = <form>_submit`、`action_type: form_submit`。
- **飞书**：裸卡片命令在上游 `_on_message` 之前拦截，并记录 p2p 的 open_id 映射。卡片与菜单按 `ChatIdentity` 构建（归属 owner、当前线程读连接库）；要求绑定且未绑定时只回绑定提示。合成命令先 `_attach_connection_identity` 再投递。卡片回调在 lark 线程里同步执行，身份解析投到主循环并限时 2 秒。`/repo` 的目录扫描在线程池里做。

## 4. 子代理与角色流水线

- `subagents.custom_agents`：requirement-analyst / architect-planner / implementer / tester / code-reviewer / integrator-verifier，全部 `thinking_enabled: true`，超时 1800–7200 秒。
- `thinking_enabled`（fork 字段）：`CustomSubagentConfig` 与 `agents.<name>` 覆盖均可设；`resolve_subagent_thinking_enabled()` 在模型不支持 thinking 时回落关闭（旧式模型配置下 `create_chat_model` 会直接抛错）。
- 渠道会话默认：`is_plan_mode: true`（todos 可见）、`subagent_enabled: true`（否则无法委派角色）、`recursion_limit: 250`（上限 `max_recursion_limit` 1000）。
- 长任务：`bash` 单命令有超时（`sandbox.bash_command_timeout` 默认 600 秒）→ 角色提示词内置 `nohup … &` + 轮询日志模式。

### pod-blanket：skill 形态的长任务业务流水线

- 分层：人设 `pod-blanket`（共享布局，不设 `skills` 白名单、`allowed_subagents: []`、`memory_enabled: false`；只用 pod-blanket 由 SOUL 约束）只调 `podctl`；引擎 `podflow` 负责全部状态。业务状态在业务库（mooya Postgres 的 `pod_blanket` 库；测试与兜底用 SQLite），不依赖聊天记忆。
- 阶段契约：每个 Pxx 是一次独立 LLM 调用，system = G00 + Pxx 原文 + 程序追加的 result JSON Schema；变量以带标题的 JSON 块放 user，图像按「输入」段顺序编号附上；外壳的 `job_id` / `stage` 以程序值为准；`run_stage(..., extra_validate, normalize)`：`normalize(外壳) -> notes` 在 schema 校验前就地归位 / 补只做记录的字段（P06 的 `_normalize_p06`：`prompt_summary` / `avoid_instructions` / `generation_parameters` / `text_overlay` / `checks` / `reference_asset_ids` / `edit_regions` / `variant_id` / `output_level` 从外壳顶层或 result 下一层的对象挪回，缺的补默认值，说明进 `StageOutput.notes` 与事件 `stage_output_normalized`）；`llm.json_objects(text)` 整段不是一个 JSON 时从第一个「{」起 `raw_decode` 依次解出相连的完整对象，`parse_envelope` 取第一个整份通过校验的（多于一个记 `stage_output_repaired`）；仍不合 schema 或 `extra_validate` 带错误说明重答（`llm.max_format_retries`；缺 `$.result` 必填项时提示写在 result 这一层），每次退回把原文写进 `logs/llm-rejects/<stage>-<scope>-<call_id>.txt`（14 天）、记事件 `stage_output_rejected {stage, call_id, errors[:12], raw}`（scope = `scope_id`）；`run_stage` 不看 envelope `status`，要不要停由调用方判断（S06 对 blocked / failed 抛错；S06 的 `StageOutputInvalid` 由 `advance_job._retry_s06` 放回队列 `llm.s06_job_retries` 次，计数从最近一次 `job_redo` 事件之后算）。
- 调用账本：每次 HTTP 请求先 `reserve`（BEGIN IMMEDIATE 核对上限、写行）→ `mark_submitted` → 发请求 → 结算。已提交却超时 = `unknown`，不自动重付费，开 `call_reconcile` 审核项；`budget.enforce: false` 时记 `untracked`、不查上限。
- 推进模型：`advance_job` 按状态决定下一步（S06 → T01 → S07 → T01R → S09 → S10；`qc_pass` 直接进 S09，旧状态 `distinct` 也进 S09），每步先落库；审核项不阻塞任务完结，人工裁决后 `reopen_job`。出图 worker（2026-10-26 起多工位，`worker.Worker`）：持主租约 `worker_lease`（120 秒，30 秒心跳；心跳同时续本进程全部 running 任务的 `jobs.lease_until`，连续失败 `LEASE_LOST_SECONDS` 90 秒算丢租约），开 `batch.workers` 条工位线程，每条循环 `_claim` → `advance_job(should_stop=…)`；生图 / LLM 请求共用进程内名额 `limits.image_slot` / `llm_slot`（`batch.image_concurrency` / `llm_concurrency`，只有 worker `configure` 后生效；等名额与发请求前 `ctx.db.close()` 放下本线程连接，`limits.release_db`）；`gen_concurrency` 仍是单个方向内的槽位并发。领什么：`--job` 给定只领这些；source 是 directions / fix 的每次现查 `worker.chosen_jobs`（`fixes.pending` + `directions.pending_jobs`），tick 来源在连续运行窗口关掉后也只领这些，其余领全部 ready；`state.claim_job(..., job_ids, order)`：`job_ids=[]` = 没有可领，`order=fair`（`batch.queue_order` 缺省）时候选里先挑有 `repair_pending + needs_changes` 素材的，再挑所在系列当前 running 最少的，同等按 `created_at, job_id`。退出：没活且所有工位空闲满 `worker_idle_seconds`（后台缺省 60、前台 0；退前 `_peek_work` 看一眼，有活就叫醒工位，看过后一个都没领到才退）→ `queue_empty`；`--batch` 领满 → `limit`；暂停 / 丢租约 → 工位在下一步前放回任务；跑满 `worker_lifetime_minutes` 或 `_Reload` 发现 `podflow.yaml` / `secrets.env` / `podflow/*.py` 变化并稳定 30 秒 → `_handoff`：先 `release_worker_lease`、拉起同 source 的接班 worker（`continued.handoff`），自己只续手上任务的租约直到工位做完当前步骤。批次反馈 S11 只由持主租约的主线程跑（单独线程、`_feedback_lock`，失败的批次本次不再试）。工位做完带人工修改的任务就 `notify.fix_finished`；摘要 `fix_cards` / `fix_only`（只做了修改时不发「出图一轮结束」）、`lanes`、`limits`（峰值）。`recover_stale` 只回收 `lease_until` 过期的 running 任务；调用只回收属于这些任务的、任务已不在跑的、不属于任务且超过 `STALE_CALL_MINUTES` 60 分钟的（拆解 / 策划 / 图案提取进程的在途调用不再误判）。`start_runs` / `fixes.start` 拉起 `worker --source directions|fix`（不带 `--job`），有 worker 在跑就只排队。`tick`（P00 程序化）只负责判断与拉起。
- 去重只剩两层：裂变时的 `plan_hash`（`variants` 唯一约束，丢 `duplicate_plan`）与 `assets.sha256` 唯一（字节完全相同不落两份）。成图不做相似度判定（S08 / P08 / `asset_dup` 已删，`dhash` / `phash` / `dedup_json` 列只留旧数据）；存量迁移 `maintenance.retire_dedup(ctx, by)`：关 `asset_dup`、`review_dup` → `qc_pass`，已结束任务当场 `step_s09` + `step_s10`，worker 存活时拒绝，可重复执行。

## 5. 模型与配置约定

- 部署配置是被追踪的 `deploy/fork/config.yaml`，根目录 `config.yaml` 是指向它的本机软链（上游 gitignore 忽略；fork CI 因此看不到它）；只写 `$VAR`；启用块放在对应注释示例块之前；fork 定制项：models、loop_detection、sandbox（host bash + mounts）、subagents、database（postgres + `$DATABASE_URL`）、run_events、channel_connections、channels。
- `models` 第一个即默认模型（title / summarization / memory 在 `model_name: null` 时复用）。
- 豆包 thinking 走 `extra_body.thinking.type`；硅基流动走 `extra_body.enable_thinking`；MiniMax-M2.5 只能开 thinking。
- mooya LiteLLM 块（`base_url http://host.docker.internal:4001/v1`、`$LITELLM_API_KEY`）：
  - **gpt-5.6：** 用 `ChatOpenAI`，档位靠模型名后缀，`supports_thinking: false`（不发思考参数，开着 thinking 也不报错），`stream_chunk_timeout: 600`。
  - **deepseek：** 用 `PatchedChatDeepSeek`（`api_base`）。
  - **接入前探测：** 新模型先跑 `scripts/fork/probe_litellm_models.py`，测对话 / 流式 / 两步工具 / 识图。
- models 改动是热加载的（下一条消息生效）；配置里每个 `$VAR` 在加载时都必须存在，所以新变量要先进 `.env` 并 `--force-recreate gateway`，再在 config 里引用。`database` 这类重启生效的段也一样（整份 config 照样会被热重读）：要么先 recreate 再改，要么在网关停着时改完再 recreate（10-29 切主库用后者）。
- 同步上游后对比新旧 `config.example.yaml` 手工合入新字段与 `config_version`，再复核 fork 定制项；**禁用 `make config-upgrade`**（`yaml.dump` 写回会删光注释）。fork 只加可选字段时不改 `config_version`。

## 6. Cursor CLI 驱动模式

- 容器启动时 `cursor-agent-setup.sh` 生成 `/usr/local/bin/cursor-agent` wrapper（先 `rm -f`，防止写穿软链）；`CURSOR_AGENT_PROXY` 覆盖代理，空值 = 直连。

## 7. 上游同步模式

- 备份 tag → `git fetch upstream` → 临时 worktree 以 `upstream/main` 为基线重建 → 逐项移植提交 → lint + 全量单测（根目录无 `config.yaml`、临时 `DEER_FLOW_HOME`）→ 用户确认后 force-with-lease → 主目录切换与容器重建单独做。
- 上游不变式要在实现侧满足：`KNOWN_CHANNEL_COMMANDS` ⊆ Telegram 注册命令 ⊆ `RESERVED_SLASH_SKILL_NAMES`（并同步 contracts 与前端）。
- 主库在 Postgres（2026-10-29 起）：上游新的 alembic 迁移会在网关启动时直接跑在 `deerflow` 库上，同步后先在测试库 `deerflow_test` 跑上游 Postgres 用例（`DEERFLOW_TEST_POSTGRES_URL`）与一次 bootstrap。
- 国内重建镜像用 `scripts/fork/rebuild-dev.sh`：`uv.lock` 临时改写为阿里云源 + 镜像 `UV_INDEX_URL` 构建 → 还原 lock → `up --no-build`；运行时容器里不能有 `UV_INDEX_URL`。

## 8. 经验教训速查

### 后端

- pod-blanket 后台循环的退出条件要排除「只在等外部」的行：`scenes sync` 曾因排着的套图都在等货号而守到 40 分钟（测试里 sleep 打桩直接死循环），现在只剩等货号就退出、交给巡检。
- pod-blanket 暂停要连自动发布一起停：只停「程序替人确认」时，进了采集箱的款照样被自动发布。飞书事件只转「变成勾」的记录，取消勾只能靠巡检回读。
- `tests/conftest.py` 会 mock 掉 `deerflow.subagents.executor`：可测逻辑放到不被 mock 的模块（如 `subagents/config.py`）。
- 上游 CI 不带 `config.yaml`：全量测试要在根目录没有 `config.yaml` 的 checkout 里跑，否则导入期读取配置的模块会因 `$VAR` 缺失报错。
- 测试默认写 `backend/.deer-flow`：宿主机跑测试一律 `DEER_FLOW_HOME=$(mktemp -d)`，否则在主目录里会污染线上数据。
- 回收「别人留下的」在途工作只能按租约过期判断，不能按「owner 不是我」：worker 启动时的 `recover_stale` 曾把正在跑的拆解进程的 P05 调用记成结果未知；多进程 / 多工位后更会互相回收。
- 变异验证要先确认目标用例存在且不改代码时是绿的，变红只认退出码 1：引用不存在的用例（退出码 4 / 5）、改出语法错误都会被误算成「变红」；同一个副本有两个执行者时变异会互相把改坏的代码当原样还原（2026-10-27 并发事故）。
- 分组上限别依赖这一次的总数：同一个分组函数先按大 want 统计个数、再按最终个数挑槽位，上限随 want 变会让计数和槽位对不上（2026-10-27 F03 换画法计数 7、实际 2）。
- 结构化阶段别为「只做记录」的字段重答：gpt-6.1-sol 会把它们写到 result 外面（2026-10-26 一天 27/76 次 P06 因此退回），由程序归位、补默认值；输出里也会出现两个 JSON（Extra data），按 `raw_decode` 取能通过校验的那个。
- 一个 worker 一次只推进一个任务、还要等最慢的槽位：一张图卡 13 分钟整条线就停 13 分钟。并发放在「工位 × 全局名额」，名额等待期间放下数据库连接（每线程一条连接，库角色上限 30）。
- 飞书卡片的构建涉及文件 IO：在主事件循环里要用 `asyncio.to_thread`；在 lark 回调线程里可以同步执行。
- 沙箱子进程会剔除名字含 KEY / SECRET / TOKEN / PASS 的环境变量，`required-secrets` 只从请求 `context.secrets` 取值（定时与 IM run 都不带）：skill 脚本的凭证放数据目录里的 600 文件。
- 沙箱 bash 只放行 `/mnt/user-data`、`/mnt/skills`、`sandbox.mounts` 与 `/usr/bin` 类系统路径：数据目录由环境变量（`DEER_FLOW_HOME`）推导，命令里不出现 `/app/...`。
- 开着 `sandbox.allow_host_bash`（LocalSandboxProvider）时，上游拒绝运行带 `skills` 白名单的 Custom Agent（`cannot enforce per-Agent skill filesystem isolation`，飞书只显示 No response）：fork 人设一律不设 `skills`，只用哪个 skill 写进 SOUL，`test_fork_personas.py` 守着。后台长进程从 `$DEER_FLOW_PROJECT_ROOT/skills/public/<skill>` 原目录启动。
- gateway 进程 PATH 首位是 venv，`docker exec` 默认是系统 Python：skill 入口自己挑解释器，并在 SKILL.md 禁止 `pip install`（agent 会自作主张装包）。
- LiteLLM 会把上游 4xx 参数错误包成 500：错误分类要看响应正文，不能只看状态码；gpt-image-2.5 的编辑接口（带输入图）不认 `format`。
- 借鉴 Mooya Pattern DNA 的提示词要先看方向：它是「守住爆款的相似衍生」（对位替换、相似度三档、默认沿用排列与留白、主体 / 配色锁定）。pod-blanket 的大变化只借拉大变化的写法（目标写成品、纯文生图不提参考图、分模型写法、文生图 / 图生图分流）；小变化（2026-10-16）才借相似度「中 / 高」两档的保留清单当构图锁。
