## 任务状态

`ready → running → complete`；中途可能进入 `blocked`（预算 / 积压 / 到时限，条件恢复后自动继续）、`failed`（尝试次数用尽）。
素材状态：`generated → qc_pass → preview_ready → archived`。分支状态：`repair_pending → superseded`（修复后由新版本接替）、`rejected`、`review_qc`、`repair_unknown`。S08 近重复判定 2026-10-13 下线（用户决定：相近的候选一并进选款），旧数据里的 `distinct` / `duplicate` 是停用前的状态。

## 恢复规则

- 同一时刻只有一个出图 worker 持有主租约；租约 120 秒，每 30 秒续一次，心跳同时续它名下全部在跑任务的租约。进程里开 `batch.workers` 条工位，每条一次推进一个方向，所有工位共用生图名额 `batch.image_concurrency` 与 LLM 名额 `batch.llm_concurrency`。
- worker 有活一直跑：来源是 directions / fix 的每次领取都现查确认过的方向和选款里要求的修改（修改先领，其余按任务轮流，`batch.queue_order`）；没活等 `batch.worker_idle_seconds` 再退出。跑满 `batch.worker_lifetime_minutes` 或配置 / 引擎代码变了就交接：先交出主租约、拉起接班的，自己做完手上几步再退出。
- worker 进程中断后，下一次 tick 或 worker 会回收：租约过期的 `running` 任务回到 `ready`；它们已提交但没有结果的生图请求转为「结果未知」，并开对账审核项，**绝不自动重新提交**。活着的 worker（包括交接中的上一任）和拆解、策划进程正在发的请求不回收。
- 人工对账登记为「未扣费」后，该槽位才允许重新提交；登记为「已扣费」的，记入成本后结束该槽位。

## 里程碑

- **M1**：1 张参考图、1 个系列，手动跑通全链路，结果可追溯；不自动发布。
- **M2**：约 12 个候选任务的受控批次；每个变更字段可核对。
- **M3**：在批准的预算内后台连续试运行 24 小时；验证重启恢复、结果未知对账、预算与积压停止；日报与异常通知。
- **M4**：增加母版与系列；每个系列要有差异化产出，反馈要能追溯到具体版本。

## 指标口径（没有数据时为 null，不按 0 计）

- 首次质检通过率 = 第一次质检即通过的图 ÷ 完成第一次质检的图。
- 质检通过率 = 通过质检进入候选库的图 ÷ 完成质检的图（修复链只算最后一版）。
- 每个候选成本 = 本批全部已结算费用 ÷ 通过质检的候选数；存在未结算调用时记为待对账。
- 人工选中率 = 人工选中的候选 ÷ 完成人工评审的候选。
